`sightmap` is the reference command-line tool (Go). It drives a real Chrome session over the Chrome DevTools Protocol, layers your `.sightmap/` corpus onto the live page, and reports annotated snapshots and coverage. It's what you author against, and what CI runs to keep a corpus healthy.

The same repository is a `go get`-able library — downstream consumers import the component model and matcher directly. See [Use as a Go library](/reference/go-library).

<Note>
This page is an orientation, grouped by job. The flag-by-flag reference lives in the [CLI reference](/cli/overview), one page per group — each section below links to its page.
</Note>

## Install

```bash
# Native binary via npm (no Go toolchain needed):
npm install -g @sightmap/sightmap
# One-off:
npx @sightmap/sightmap snapshot ...
# From source:
go install github.com/sightmap/sightmap/go/cmd/sightmap@latest
```

Install the agent skills into your harness (defaults to `~/.agents/skills/`):

```bash
sightmap skills install
```

This installs two skills: `sightmap-authoring` (building and maintaining a corpus) and `sightmap-browser` (driving a live session). The overlay browser extension is embedded in the binary and auto-extracted on first `browser start` — no flags needed. All install paths are on [Install](/start/install).

## Conventions

Two conventions hold across the surface:

- Most commands accept `--sightmap-dir DIR` to point at a corpus outside the current directory (default `.sightmap`).
- Exit codes are uniform: `0` success, `1` failure. `validate` exits `1` on any structural error; `lint` exits `1` on warnings unless you pass `--warn-only`.

## Sessions

`sightmap browser` owns the Chrome session. `start` launches Chrome plus a local server that hot-reloads the corpus as you edit YAML, so the loop never pauses for a restart.

| Command | What it does |
|---|---|
| `browser install` | Download a managed Chrome for Testing build to `~/.sightmap/browsers/` |
| `browser start` / `browser stop` | Launch (and stop) Chrome plus the sightmap server |
| `browser launch` | Lower-level Chrome launcher, including `--headless` |
| `browser status` | Session health, CDP address, and open content tabs |
| `browser navigate` / `browser eval` | Navigate (positional URL) and evaluate JavaScript in the page |
| `browser clear-storage` | Wipe cookies and storage to reset session state |

Full reference: [Browser sessions](/cli/browser).

## Interaction

`browser click`, `fill`, `hover`, `keypress`, `scroll`, `drag`, `wait-for`, `dialog`, and `bounds` act on the live page. Targets are a numeric probe ID from snapshot output or — preferred on dynamic pages — a component query like `ProductCard[name^="Weber"]`, which resolves and acts atomically so a re-render can't stale the handle.

| Command | What it does |
|---|---|
| `browser click` / `browser hover` | Click or hover a component by ID, component query, or coordinates |
| `browser fill` | Type into a field (`--clear` for React-controlled inputs) |
| `browser keypress` | Send a key: Enter, Tab, Escape, arrows, and more |
| `browser scroll` / `browser drag` | Scroll by delta (optionally scrolling a component into view first) or drag |
| `browser wait-for` | Block until a URL pattern, a selector, or the load event |
| `browser dialog` | Accept or dismiss a JavaScript dialog |
| `browser bounds` | Viewport-relative bounding boxes for components, as JSON |
| `browser screenshot` | Save a PNG of the current page |
| `browser tabs` | `list` / `new` / `select` / `close` / `resize` for multi-tab work |

Full reference: [Interaction](/cli/interaction).

## Capture

Three ways to look at a page, from fastest to deepest:

| Command | What it does |
|---|---|
| `iterate` | Navigate + snap + coverage in one step — the primary authoring loop |
| `snapshot` | The annotated component tree; records timestamped captures into the view's set |
| `inspect` | The raw DOM tree, for finding selector anchors |

`snapshot --all` refreshes a capture for every URL declared in `views/*.yaml`. A view's captures accumulate as a set under `.sightmap/snapshots/{view}/`, scored as a union and guarded by a novelty gate that skips re-snaps adding nothing structurally new. The set-maintenance commands — `snapshot-novelty`, `snapshot-prune`, `migrate-snapshots` — are documented with the model itself in [View sets](/cli/snapshots).

Full reference: [Capture](/cli/capture).

## Coverage

Coverage scores every interactive node: T1 directly matched (maximize), T2 unnamed inside a matched ancestor (acceptable when tight), T3 orphaned (must reach 0).

| Command | What it does |
|---|---|
| `coverage` | Offline T1/T2/T3 check over saved captures |
| `multi-coverage` | Cross-view coverage matrix — surfaces components to promote to global |
| `report` | Per-view coverage health table with T2 quality |

Full reference: [Coverage](/cli/coverage).

## Selector tooling

Never write a selector into YAML without verifying it first — a wrong match count corrupts coverage.

| Command | What it does |
|---|---|
| `sel-probe` | Validate a selector against the live page: match count, attributes, parent chain |
| `sel-check` | Validate a selector offline against a saved capture |
| `suggest` | Candidate selectors from the live DOM (`--exclude-known` hides what's already mapped) |
| `gap` | Orphaned interactive nodes on the live page, with selector hints where it can anchor them |

Full reference: [Selector tools](/cli/selectors).

## Corpus hygiene

The checks that keep the YAML itself healthy — `validate`, `lint`, and `search` run without a browser, which makes them natural CI steps.

| Command | What it does |
|---|---|
| `validate` | Structural check against the spec — exits `1` on error |
| `lint` | Advisory style checks (use `--warn-only` to always exit `0`) |
| `search` | Offline content search across the corpus (`--field` narrows to name, selector, description, or memory) |
| `discover` | Classify the site's URL patterns against the corpus: mapped, surveyed, unseen (needs a live session) |

Full reference: [Corpus hygiene](/cli/corpus).

## Integrations

| Command | What it does |
|---|---|
| `serve-sightmap` | Serve the compiled corpus over HTTP for the overlay browser extension, standalone |
| `skills install` | Install the `sightmap-authoring` and `sightmap-browser` agent skills into your harness |
| `version` | Print the CLI version |

Full reference: [Integrations](/cli/integrate).

## The loop in one screen

```bash
cd my-app                       # a project with a .sightmap/ corpus
sightmap browser start          # Chrome + corpus server
sightmap iterate 'http://localhost:3000/products'
```

`iterate` prints per-view coverage and, for orphaned (T3) clusters it can anchor, a suggested selector. Verify it, then add a component to `.sightmap/`:

```bash
sightmap sel-probe '[data-testid="product-pod"] button[data-testid="atc"]'
```

Re-run `iterate` until coverage reports `0 orphaned T3 ✓`, then check the whole corpus:

```bash
sightmap validate            # structural correctness
sightmap lint --warn-only    # advisory style checks
sightmap report              # per-view T1/T2/T3 health table
```

The full loop — including T2 triage and cross-view promotion — is the [authoring overview](/authoring/overview).
