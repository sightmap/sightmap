Definitions used throughout the Sightmap docs and spec. Alphabetical.

### Audit

A maintainer or contributor task that compares the live `.sightmap/` directory against the actual codebase to catch drift — stale routes, missing components, dead memory entries. Audits are typically run before a release or after a large refactor.

### Bootstrap

The first generation of a `.sightmap/` directory for a project, produced by an agent driving the running app with the [`sightmap` CLI](/cli/overview) and proposing an initial set of views and components from what it observes. The author then curates the output. See [the authoring workflow](/authoring/overview).

### Capture

One timestamped snapshot of a view, stored at `.sightmap/snapshots/{view}/{stamp}.snap` with a sibling `.snap.tree.json` file holding the raw component tree. A view's captures together form its **view set**. See [Snapshots](/cli/snapshots).

### Component

A named DOM subtree, identified by one or more CSS selectors. The unit of UI naming Sightmap surfaces to agents. Defined under `components:` either at the file root (global) or inside a view (scoped). See [Components](/spec/components).

### Component query

A small query language for targeting components by name and extracted property values — for example `ProductCard[name^="Weber"]` or `Ancestor Descendant`. Accepted by `sightmap browser click`, `fill`, `hover`, and `scroll` in place of a component ID from `sightmap snapshot` output; the query resolves against a fresh extraction in one atomic pass, so it survives re-renders that invalidate previously captured component IDs. See [Interaction](/cli/interaction).

### Conformance

The contract a Sightmap implementation honors. Conforming implementations are validated against the language-agnostic [conformance fixtures](/reference/conformance-fixtures) and the requirements in the [schema reference](/reference/schema#conformance).

### Consumer

A program that reads a sightmap at runtime — typically an agent, a snapshot enricher, or a network-trace tool. Consumers honor the spec; they do not produce sightmap files. Contrast with **Curator**. See [Curator vs. consumer](/concepts/curator-vs-consumer).

### Corpus

The merged contents of a project's `.sightmap/` directory — every discovered YAML file combined into one set of views, components, and requests — as loaded by the CLI and the [Go library](/reference/go-library). `validate`, `lint`, `search`, and the coverage commands operate on the corpus as a whole, not on individual files. See **`.sightmap/` (the directory)** below.

### Coverage tiers

The three-tier score the CLI assigns every interactive node in a capture. **T1 direct** — the node itself is matched by a component selector; maximize this. **T2 scoped** — the node sits inside a matched ancestor but is unnamed itself; acceptable when the scope is tight. **T3 orphaned** — no matched ancestor at any depth; must reach 0. See [Coverage](/cli/coverage).

### Curator

A human (or human-supervised agent) who authors and maintains the `.sightmap/` directory. Curators choose which UI surfaces are worth naming, write memory entries, and keep the corpus in sync as the app evolves. Contrast with **Consumer**.

### Glossary (this page)

Where these terms are defined. If a term is missing, open a [Discussion](https://github.com/sightmap/sightmap/discussions).

### MCP

[Model Context Protocol](https://modelcontextprotocol.io/) — the protocol some agent hosts use to expose tools to agents. Sightmap itself is transport-agnostic: the `.sightmap/` corpus is plain files, and any tool (MCP-based or not) can read it.

### Memory

Short freeform notes attached to a file, view, component, or request. Memory carries context that isn't recoverable from the source code: quirks, invariants, "you have to click this twice" lore. See [Memory](/spec/memory).

### Novelty gate

The rule that decides whether a re-snap of a view is kept: a capture is saved only if it adds something structurally new relative to the view set — a new component type matched, or a new uncovered interactive slot. Pure value churn (different products, prices, copy) never counts, so dynamic views saturate instead of accumulating near-duplicate captures. `sightmap snapshot --force` overrides the gate. See [Snapshots](/cli/snapshots).

### Project semver

The [SemVer](https://semver.org/) version of the `sightmap/sightmap` repo (currently `0.1.0`), published on GitHub Releases. Tracks docs, schema clarifications, examples, and tooling cadence. Independent of the spec stream version. See [Versioning policy](/reference/versioning).

### Request

A named API endpoint described in the sightmap. Carries the route glob, HTTP method, payload shape, and optional memory. Defined under `requests:`. See [Requests](/spec/requests).

### Selector

A CSS selector (or array of alternatives) that locates a component's root element. Child selectors are scoped to the matched parent's subtree. See [Selectors](/concepts/selectors).

### Sightmap (the file)

A single YAML document under `.sightmap/` that conforms to the v1 schema. "A sightmap" can also refer to the whole `.sightmap/` directory, depending on context.

### `.sightmap/` (the directory)

The conventional location for a project's sightmap files. Lives at the repo root. All `*.yaml` and `*.yml` files inside (recursively) are discovered and merged into the **corpus**; the `snapshots/` and `review/` subdirectories are skipped during corpus loading.

### Stream version

The integer in a sightmap file's `version:` field — currently `1`. Identifies which spec stream the file conforms to. Bumps only on a breaking change to the YAML format. Independent of the project semver. See [Versioning policy](/reference/versioning).

### View

A named screen in the app, identified by a URL route glob. The unit of routing Sightmap matches against the current page. Defined under `views:`. See [Views](/spec/views).

### View set

All captures for a single view. Coverage is scored over the **union** of the set, because real pages are non-deterministic — lazy carousels, personalization, and rotating promos mean a single capture can miss whole sections. See [Snapshots](/cli/snapshots).
