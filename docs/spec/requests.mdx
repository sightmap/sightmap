A request is a named API endpoint. Names replace raw URLs in network traces, so an agent inspecting traffic sees `SearchFlights` instead of `POST /api/flights/search`.

```yaml
- name: SearchFlights
  route: /api/flights/search
  method: POST
  source: src/api/flights.ts
  request:
    fields:
      - name: origin
        type: string
        description: IATA code
      - name: destination
        type: string
        description: IATA code
      - name: departureDate
        type: string
        description: ISO-8601 date
  response:
    fields:
      - name: results
        type: array
  headers: [x-request-id]
```

`name` and `route` are required. See [Schema reference](/reference/schema#request) for the full type, including the `Payload` and `Field` sub-types.

## Route patterns

Request routes use the same glob syntax as views — `*` for one segment, `**` for any depth — with one addition: **Express-style `:param` segments are normalized to `*`**. These two are identical:

```yaml
- route: /api/users/:id/orders    # same as below
- route: /api/users/*/orders
```

The named form exists because Express, Next.js API routes, and most JS frameworks already write routes that way; you can paste a route in unchanged. The runtime treats both identically.

## Method filter

`method` is an optional HTTP method filter — `GET`, `POST`, `PUT`, etc. — matched case-insensitively. If omitted, the route matches any method. With it set, only matching methods are named.

```yaml
- name: GetUser
  route: /api/users/:id
  method: GET

- name: UpdateUser
  route: /api/users/:id
  method: PATCH
```

Two definitions can share a route as long as they differ on method. Conformance fixture `007-request-method-filter` covers this case.

## All matches apply

Requests are matched independently. **Every** request whose `route` matches the URL — and whose optional `method` matches the request method — applies. There is no "winning" request; all matches contribute to the enriched output.

```yaml
requests:
  - name: SearchFlights
    route: /api/flights/search    # specific
  - name: AnyFlightsCall
    route: /api/flights/**        # catch-all
```

A `POST /api/flights/search` matches **both** `SearchFlights` and `AnyFlightsCall`, and both names apply. Declaration order changes nothing, and there is no need to list specific routes before general ones.

<Note>
This is the opposite of view matching, where exactly one view wins by specificity. See [Views](/spec/views#most-specific-wins) for that rule.
</Note>

## Payloads are documentary

`request` and `response` describe the expected payload shape. Both are `Payload` objects — `{ fields: [...] }` — where each field has a `name` (required), a free-text `type` label (`string`, `number`, `boolean`, `array`, `object`, or anything else), and an optional `description`.

The listed fields are not exhaustive and are not enforced: extra fields in real-world traffic are never rejected. They document what an agent should expect to see, nothing more.

`headers` lists notable header names to highlight in the network detail view:

```yaml
- name: GetCurrentUser
  route: /api/me
  method: GET
  description: Returns the current user, or 401 if unauthenticated
  response:
    fields:
      - name: id
        type: string
      - name: email
        type: string
```

## Scoped vs global

Like components, requests can live at the file root or inside a view.

- **Global** (file root): matched on every view.
- **View-scoped** (inside a view): matched only when that view is active.
- Additive: a view sees its own requests plus all globals. See [Views](/spec/views#scoped-vs-global).

Most apps put requests at the file root — the same `/api/users/:id` is meaningful regardless of which view is showing. Scope to a view when an endpoint is genuinely page-specific.
