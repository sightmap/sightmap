A sightmap is a directory of YAML files at the root of a project, under `.sightmap/`. It describes the app's **views**, **components**, and **requests**, plus corpus-root **messages** (console and exception patterns) and **signals** (named state predicates), with optional **memory** entries that carry notes agents can use at runtime.

These pages explain the format. The [Schema reference](/reference/schema) provides the field-by-field contract and is generated from [the canonical spec](https://github.com/sightmap/sightmap/blob/main/spec/v1/schema.md).

## What's in a sightmap

Six kinds of definitions, all optional:

  <Card title="Components" icon="puzzle-piece" href="/spec/components">
    Named DOM subtrees identified by CSS selectors.
  </Card>
  <Card title="Requests" icon="arrow-right-arrow-left" href="/spec/requests">
    Named API endpoints identified by route patterns.
  </Card>
  <Card title="Messages" icon="message" href="/spec/messages">
    Named console-output and exception patterns, matched by level and regex.
  </Card>
  <Card title="Signals" icon="signal" href="/spec/signals">
    Named boolean predicates over an existing component or view.
  </Card>
  <Card title="Memory" icon="brain" href="/spec/memory">
    Short freeform notes attached to files, views, components, and requests.
  </Card>
</CardGroup>

Every `*.yaml` and `*.yml` file under `.sightmap/` is discovered recursively and merged. Merging appends each top-level collection (`views`, `components`, `requests`, `messages`, `signals`) across files. The directory layout is for authors; it has no semantic meaning.

## Top-level fields

Every file begins with `version: 1`. All other top-level keys are optional.

```yaml
version: 1
url:         # string — default representative URL for views in this file
memory:      # string[] — file-level notes
views:       # View[]
components:  # Component[] — global, matched on every view
requests:    # Request[] — global, matched on every view
messages:    # Message[] — console/exception patterns, corpus-root only
signals:     # Signal[] — named state predicates, corpus-root only
```

`components` and `requests` at the file root are global and match against every view. Nest them inside a view to limit them to that view. Scoped definitions are additive with globals, except that a view-scoped `$ref` subsumes a global component with the same name. Entries in any `components:` array may be `$ref` references to shared definitions. See [Components](/spec/components) and [Requests](/spec/requests) for the matching rules.

`messages` and `signals` exist only at the file root; neither has a view-scoped form. See [Messages](/spec/messages) and [Signals](/spec/signals).

The JSON Schema also permits a file-level `snapshots:` list. It is a [reserved tooling field](/reference/schema#reserved-tooling-fields) used by capture tooling, not part of matching or merge semantics.

## Two versioning axes

The spec and the project that publishes it move independently.

- **The spec stream** is the integer in the YAML `version:` field. It is currently `1` and changes only when the format has a breaking change.
- **The project semver** describes how settled stream `1` is. It is currently `0.1.0`. Before `1.0.0`, the spec may be tightened or clarified in place. Project releases are published on [GitHub Releases](https://github.com/sightmap/sightmap/releases). After `1.0.0`, the rules in [Versioning](/reference/versioning) become commitments.

We aim to keep the spec at stream `1` for a long time. A `version: 2` would mean a new `spec/v2/` directory and a real, accepted breaking change.

## A small example

```yaml .sightmap/home.yaml
version: 1

views:
  - name: Home
    route: /
    components:
      - name: SearchBox
        selector: '[data-component="SearchBox"]'
```

This file defines one view and one view-scoped component. Other files can add views, nested components, glob routes, requests, messages, signals, and memory entries.

<Warning>
Quote attribute selectors so YAML parses them as strings: `selector: '[data-component="X"]'`. Unquoted, the brackets are read as a YAML flow sequence and the entry fails validation.
</Warning>
