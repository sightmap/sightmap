A component is a named DOM subtree, identified by one or more CSS selectors. Names replace the generic accessibility role in enriched snapshots, so an agent reading the page sees `DepartureDatePicker` instead of `group`.

```yaml
- name: DepartureDatePicker
  selector: '[data-picker="departure"]'
  source: src/components/DatePicker.tsx
  children:
    - name: date-input
      selector: input
    - name: day
      selector: '[role="gridcell"]'
```

`name` and `selector` are required. See [Schema reference](/reference/schema#component) for the full field list, including `description`, `source`, `memory`, `properties`, `tags`, and `stability`.

## Selectors

`selector` accepts a single CSS selector string or an array of strings:

```yaml
# Single selector
- name: SubmitButton
  selector: 'button[type="submit"]'

# Array — alternatives tried in order, first match wins
- name: OriginAirportPicker
  selector:
    - '[data-picker="origin"]'
    - '#origin-combobox'
```

Use the array form to keep one name across UI variants, such as a redesigned page, a feature flag, or a third-party widget. Sightmap tries each selector in order and uses the first one that matches one or more elements.

If a selector matches multiple elements, all matches get the name. Selectors are not required to be unique.

Selectors match against the captured component tree, which is a flattened representation: each shadow root's content appears as ordinary children of its host. Selectors therefore match across shadow boundaries with no piercing syntax. A tool that re-implements matching against the live DOM MUST traverse shadow roots to agree with the corpus. See [Selector semantics](/reference/schema#selector-semantics).

## The `data-component` convention

The recommended pattern is to render a `data-component="<Name>"` attribute on the root element of each named component, then select on that attribute:

```tsx
<nav data-component="Navigation">…</nav>
```

```yaml
- name: Navigation
  selector: 'nav[data-component="Navigation"]'
```

This keeps the sightmap independent of class names, CSS modules, and styling changes. It adds one searchable attribute to each named component.

The spec accepts any CSS selector; `data-component` is the recommended convention.

## Children are scoped

Selectors inside `children` are evaluated within their parent's matched subtree instead of against the whole document. Two card components can therefore each contain a child selected by `button.primary` without colliding.

```yaml
- name: SearchCard
  selector: '[data-component="SearchCard"]'
  children:
    - name: submit
      selector: 'button.primary'   # only inside SearchCard's subtree

- name: BookingCard
  selector: '[data-component="BookingCard"]'
  children:
    - name: submit
      selector: 'button.primary'   # only inside BookingCard's subtree
```

## Scoping inside views vs at file level

Components at the file root are global and match on every view. Components nested inside a view apply only to that view. Both forms are additive, except that a view-scoped `$ref` subsumes a global component with the same name. See [Views](/spec/views#scoped-vs-global) for the full rule.

<Warning>
Quote attribute selectors so YAML parses them as strings: `selector: '[data-component="X"]'`. Unquoted, the brackets are read as a YAML flow sequence and the entry fails validation.
</Warning>

## Referencing shared components

When a component such as a site header, persistent footer, or chat widget appears across views, a `components:` array can contain a reference object instead of another inline definition:

```yaml
- $ref: SiteHeader
```

Before matching, the reference expands inline to a deep copy of the named component. Any `$ref` entries in its `children:` expand recursively. Names resolve against a registry built from the root-level `components:` arrays of all loaded files; nested children and view-scoped definitions are not addressable. For duplicate registry names, the first definition in source-file path order wins. Implementations SHOULD emit a `merge-collision-component` warning.

```yaml .sightmap/components.yaml
version: 1

components:
  - name: SiteHeader
    selector: '#site-header'
    children:
      - name: SearchBox
        selector: 'form#header-search'
```

```yaml .sightmap/views/plp.yaml
version: 1

views:
  - name: PLP
    route: /b/**
    components:
      - $ref: SiteHeader     # attests SiteHeader is expected on this view
      - name: ProductGrid    # view-specific
        selector: '[data-component="ProductGrid"]'
```

Use `$ref` for reuse and attestation:

- **Reuse.** Update the header's selector or memory entries in one definition; every referencing view receives the change.
- **Attestation.** A view's `components:` lists what it expects to contain. Drift-detection tools can report an attested component that matches zero elements separately from a component the view never referenced.

The conformance rules:

- A `$ref` entry MUST contain exactly one key (`$ref`); overrides are not allowed in v1.
- A `$ref` to a name that isn't in the registry is a `ref-unresolved` error.
- A self-referential chain (`A` → `B` → `A`) is a `ref-circular` error.
- When a view-scoped `$ref` and a file-root global share a name, the view-scoped expansion **subsumes** the global for that view — implementations MUST NOT produce two matches.

See the [schema reference](/reference/schema#component-references) for the full statement.


## Properties

A component can declare `properties:`, which are named values shown alongside the component name in enriched snapshots. An agent then sees what matched and what state it is in, such as `[DateFilterButton label="This Weekend"]`.

Property values resolve **over the component tree**. A value comes from the matched component's own node or from the properties of components nested beneath it, never from arbitrary DOM. Resolution therefore works offline against a serialized tree, and on any UI platform that produces one.

```yaml
- name: DateFilterButton
  selector: '[data-testid="date-filter-button"]'
  properties:
    - name: label
      extract: text              # → [DateFilterButton label="This Weekend"]

- name: ProductCard
  selector: '[data-testid="product-pod"]'
  properties:
    - name: price
      extract: Price.text        # a property of the Price child
    - name: sold_out
      extract: exists:SoldOutBadge   # "true" when the child matched; omitted otherwise
  children:
    - name: Price
      selector: '[data-testid="price"]'
      properties:
        - name: text
          extract: text
    - name: SoldOutBadge
      selector: '[aria-label="Sold Out"]'
```

Each property has a `name` and an `extract` directive. `name` must match `^[a-z][a-z0-9_]*$` and be unique within the component. `extract` must be exactly one of these forms; validation rejects any other value:

| Form | Resolves to |
|---|---|
| `text` | The node's accessible text (its accessible name) |
| `raw_text` | The node's own literal text: its direct text-node children, whitespace-normalized |
| `attr=NAME` | The value of attribute `NAME` in the node's observed attribute set |
| `PATH.prop` | The value of property `prop` on the descendant component addressed by `PATH` |
| `exists:PATH` | `"true"` when `PATH` resolves to at least one matched component |

`PATH` is a dotted sequence of component names, such as `Price` or `Row.Price`. Each segment resolves to the first match, in document order, within the previous segment's matched subtree. References only descend: a property can address a component nested beneath the one that declares it, never a parent, sibling, or cousin. To read a value from a sub-element, declare that sub-element as a child component and reference its property.

The attribute set that `attr=NAME` reads is implementation-defined. A web consumer might carry a fixed allowlist plus `aria-*` and `data-*` attributes, and other platforms carry synthetic attributes. An attribute the consumer did not carry is indistinguishable from an absent one.

### `text` vs `raw_text`

`text` is the accessible name, which is what a user perceives as the label. It can include text from `aria-label`, an associated `<label>`, or CSS `::before`/`::after` content. `raw_text` is the node's own author-written text. It excludes descendant elements and pseudo-element content, and every consumer computes it identically, live or offline.

Use `text` when the accessible name is the value you want, such as an icon button labeled only by `aria-label`. Use `raw_text` when the accessible name includes extra text. For example, a heading `<h3>Main</h3>` with a `::after` badge reading "Most popular" has the accessible name "Main Most popular", while its `raw_text` is "Main". See [SEP-0013](https://github.com/sightmap/sightmap/blob/main/spec/seps/0013-richer-node-data.md).

### Omission and the reserved `value` name

Value omission is silent. When a property's text is empty, its attribute is not carried, or its `PATH` matches nothing, the property is dropped from the annotation. Consumers MUST NOT treat omission as an error.

The name `value` is reserved. You can declare it to override the accessibility tree's own value, and implementations MUST prefer a declared `value` over the AX value.

<Note>
This tree-closed model is defined by [SEP-0010](https://github.com/sightmap/sightmap/blob/main/spec/seps/0010-tree-closed-component-properties.md), which supersedes the extraction model of [SEP-0003](https://github.com/sightmap/sightmap/blob/main/spec/seps/0003-component-properties.md). The earlier DOM modes (`inner_text`, `text_only`, `inner_html`, and bare CSS sub-selectors) and the `transform` field are no longer valid. To migrate, promote the sub-element to a child component and reference it with `PATH.prop` or `exists:PATH`.
</Note>

See the [schema reference](/reference/schema#component-properties) for the normative statement.

## Tags and stability

A component can carry `tags:`, a list of open-vocabulary classification labels such as `defect`. Tags resolve differently from names. A node's name comes from the nearest enclosing match, but its tags are the union across every matching ancestor level. A `SubmitButton` child of a `CheckoutForm` tagged `defect` resolves to `name: SubmitButton` and `tags: [defect]`. Implementations deduplicate the resolved set and SHOULD emit it in sorted order. See [Tags](/reference/schema#tags) and [SEP-0004](https://github.com/sightmap/sightmap/blob/main/spec/seps/0004-component-tags.md).

`stability` records how much you trust a selector: `uncertain` means it is a best guess, and `unstable` means it is known to break across renders. Omit it for a stable component. It is advisory and does not change matching. See [Stability](/reference/schema#stability).

## Dependencies

A component can list supplementary files whose changes should prompt re-curation, such as style modules, hooks, or shared utilities:

```yaml
- name: DepartureDatePicker
  selector: '[data-picker="departure"]'
  source: src/components/DatePicker.tsx
  dependencies:
    - src/components/DatePicker.module.css
```

`dependencies` is curation-time metadata. Each string is a project-root-anchored minimatch glob; prefix it with `!` to negate it. Runtime consumers MUST NOT add page-load cost based on this field. See the [schema reference](/reference/schema#dependencies) for usage rules.
