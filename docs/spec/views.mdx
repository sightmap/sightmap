A view is a named screen in the app, identified by a URL route. Components and requests nested under a view apply only when that view is active.

```yaml
version: 1

views:
  - name: FlightSearch
    route: /search
    description: Main search page with date and origin/destination pickers
    source: src/pages/FlightSearch.tsx
    components:
      - name: DepartureDatePicker
        selector: '[data-picker="departure"]'
    requests:
      - name: SearchFlights
        route: /api/flights/search
        method: POST
```

`name` and `route` are required. `url` gives the view a representative URL — a concrete address that resolves to it — which tooling uses to navigate to the view (coverage reporting, bulk capture, and probing); a file-level `url` supplies a default for views that omit their own. `description` records the view's purpose, and `source` links it to a source file. `properties`, `tags`, `environments`, and `origins` are covered below. See [Schema reference](/reference/schema#view) for every field.

## Route matching

Routes use glob patterns against the URL pathname.

- `*` matches exactly one path segment: `/users/*` matches `/users/42`, not `/users/42/edit`.
- `**` matches any depth of segments: `/admin/**` matches `/admin`, `/admin/users`, and `/admin/users/42/edit`.
- Literal segments match themselves.
- Matching is case-sensitive. Fragments are ignored, and so is the query string unless the route names query conditions (below). Trailing slashes are normalized away before matching.

For requests, Express-style `:param` segments are normalized to `*`, so `/api/users/:id/orders` and `/api/users/*/orders` are equivalent. See [Requests](/spec/requests).

### Query conditions

When one path serves several screens told apart by a query parameter, a route can end in query conditions:

```yaml
views:
  - name: ProfileMenu
    route: /en-us/profile
  - name: GiftCards
    route: /en-us/profile?section=gift-cards   # this value of section
  - name: Document
    route: /page?id=:id                        # id present, any value
```

Each condition reads the first value of its key, decoded, and compares case-sensitively. `KEY=VALUE` requires that value (a `*` inside it is a wildcard within the value); `KEY=:name` and `KEY=*` require the key to be present with any value. Every condition must hold, and keys the route does not name are ignored. A `KEY=:name` condition binds nothing; read the value with `from: url.query`. See [Route matching](/reference/schema#query-conditions).

## Most specific wins

When more than one view route matches a URL, the route with the highest specificity score wins. Declaration order breaks ties between routes with equal scores.

Specificity is the sum of per-segment scores:

| Segment | Query condition | Score |
|---|---|---|
| Literal (e.g. `users`) | `KEY=VALUE` | 3 |
| `:param` (e.g. `:id`) | `KEY=:name` | 2 |
| `*` (single segment) | `KEY=*` | 1 |
| `**` or empty | | 0 |

The root route `/` scores `1` — more specific than any wildcard-only pattern. When two routes score equal, the **first declared** view wins.

```yaml
views:
  - name: UserProfile
    route: /users/*        # score 3+1 = 4
  - name: UserAdmin
    route: /users/admin    # score 3+3 = 6
```

`/users/admin` matches both routes and resolves to `UserAdmin`. `/users/42` matches only `UserProfile`.

A query condition scores as the segment it mirrors, so `/en-us/profile?section=gift-cards` (9) wins over `/en-us/profile` (6) on that section, and `/en-us/profile` keeps every other URL at that path.

<Note>
This specificity rule applies only to views. Every matching request applies. See [Requests](/spec/requests#all-matches-apply).
</Note>

## Scoped vs global

Components and requests can live at the file root or nested inside a view.

- **Global** (file root): matched against every view.
- **View-scoped** (inside a view): matched only when that view is active.
- **Additive**: a view receives its scoped definitions and all globals. A view-scoped `$ref` subsumes a global component with the same name for that view.

```yaml
components:
  - name: Navigation                # global — matched on every view
    selector: 'nav[data-component="Navigation"]'

views:
  - name: Dashboard
    route: /dashboard
    components:
      - name: DashboardLayout       # scoped — only on /dashboard
        selector: '[data-component="DashboardLayout"]'
```

<Warning>
View names should be unique across the sightmap. Runtime behavior is implementation-defined when two files define the same view name. Conforming implementations SHOULD emit a warning.
</Warning>

## URL properties

A `:name` segment in a view route **binds** that segment's value as a property, with no declaration needed. An optional `properties` list names query-string values, or renames a bound segment, using the same `extract` object components use:

```yaml
views:
  - name: ProductDetail
    route: /shop/p/:product_id        # binds product_id
    properties:
      - name: variant
        extract: { from: url.query, path: variant }
```

On `/shop/p/12345?variant=blue` the view carries `product_id="12345"` and `variant="blue"`. Values are percent-decoded, query keys are case-sensitive, and a repeated key resolves to its first occurrence. An `extract: { from: url.path, path: product_id }` entry renames the binding, and the original `product_id` name is no longer produced.

Binding changes what `:param` produces, never what it matches: the route scores and matches exactly as before. URL properties read only the URL string, so they resolve offline, from a saved session or a coverage report.

A binding name must match `^[a-z][a-z0-9_]*$`. A segment like `:orgId` still matches but binds nothing, and `sightmap validate` warns `route-param-unbound`. A declared property that reuses a name the route still binds is an error (`route-binding-conflict`).

<Note>
Naming a URL part asks a consumer that scrubs URLs to keep it, but it is not a privacy grant. A consumer must not retain a value its own policy, or the corpus's [`privacy`](/spec/components#privacy), would withhold.
</Note>

See the [schema reference](/reference/schema#url-properties) and [SEP-0008](https://github.com/sightmap/sightmap/blob/main/spec/seps/0008-url-properties.md).

## Tags

A view's `tags` resolve as a union across **every** view whose route matches the URL, not only the most specific one. A broad `/checkout/**` view tagged `defect` therefore tags `/checkout/payment` too, even when a narrower, untagged view wins identity there. `sightmap snapshot` prints the resolved set on a `tags:` line under the view header. See [Tags](/reference/schema#tags).

## Environments and origins

`environments` and `origins` on a view name the deploy targets it exists in and the hosts it is served from. They are declarative metadata and never change which URLs the route matches. See [Environments and origins](/spec/environments).
