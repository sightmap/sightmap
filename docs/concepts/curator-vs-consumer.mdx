---
title: "Curator vs. Consumer: Who Writes a Sightmap and Who Reads It"
sidebarTitle: "Curator vs. Consumer"
description: "Separate the tools that author and maintain .sightmap/ from the tools that load and apply it."
---

**Curators** write and maintain `.sightmap/`. **Consumers** load the resulting corpus and apply it to the running app. A tool can support both roles, but each role has a different responsibility.

## Curators decide what the map says

A curator can be a human, an agent, or both working together. The curator:

- Names views, components, and requests.
- Chooses selectors and verifies them against the live DOM.
- Links definitions to source files.
- Records useful runtime behavior in `memory`.
- Updates or removes definitions when the app changes.

The [`sightmap` CLI](/cli/overview) supports this work with live browser snapshots, selector probes, and coverage reports. The bundled [`sightmap-authoring`](https://github.com/sightmap/sightmap/blob/main/go/skills/sightmap-authoring/SKILL.md) skill gives an agent the edit-and-verify workflow.

Curation still requires judgment. Coverage can find an unnamed button, but it cannot decide whether that button deserves its own component, which semantic name will remain useful, or whether an observed behavior belongs in `memory`. When an agent drafts the YAML, a human can review the same diff as any other code change.

## Consumers apply the map

A consumer reads `.sightmap/` without deciding what it should contain. Consumers include browser clients that enrich accessibility snapshots, coding agents that use source links and memory, IDE integrations that show named components, and CI jobs that validate the corpus.

A consumer implements the matching rules in the spec:

1. Load and merge the YAML files under `.sightmap/`.
2. Match the current URL to a view.
3. Apply global and view-scoped components and requests.
4. Try selector alternatives in order and scope child selectors to their parent.
5. Surface applicable `memory` entries with the enriched output.

The [Go library](/reference/go-library) implements corpus loading and matching. Other implementations can use the [JSON Schema](/reference/json-schema) and [conformance fixtures](/reference/conformance-fixtures) as their contract.

If you are maintaining `.sightmap/`, continue to the [authoring workflow](/authoring/overview). If you are adding Sightmap support to another tool, start with the [schema reference](/reference/schema#conformance).
