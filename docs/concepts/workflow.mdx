A `.sightmap/` directory is not written once and forgotten. It moves with the app: routes change, components get renamed, a quirk that justified a memory entry gets fixed, a new endpoint appears. Curation is a recurring job — **bootstrap** then **maintain** — and it's agent-driven, against the running app.

`.sightmap/` is curated authority, not a generated artifact. The live browser is the bridge: the annotated snapshot shows what the app actually rendered, and the agent reconciles the YAML against it.

## Bootstrap: get an initial `.sightmap/` from the running app

Most projects start with no `.sightmap/` directory. An agent, following the [`sightmap-authoring` skill](https://github.com/sightmap/sightmap/blob/main/go/skills/sightmap-authoring/SKILL.md), drives the app with the [`sightmap` CLI](/authoring/cli):

<Steps>
  <Step title="Start a session">
    `sightmap browser start` launches Chrome and the sightmap server.
  </Step>
  <Step title="Walk each route">
    `sightmap iterate <url>` snaps the page and scores coverage. Every interactive node is T1 (directly matched by a named component), T2 (unnamed but inside a matched ancestor), or T3 (orphaned).
  </Step>
  <Step title="Name the orphans">
    The agent adds views and components to `.sightmap/*.yaml`, choosing selectors from stable (`data-component`, `data-testid`) to fragile (ARIA, semantic tags, ids), and verifying with `sightmap sel-probe`. Where no stable selector exists, it proposes adding a `data-component` marker to the source.
  </Step>
</Steps>

The structural fields are curated against the running app; `source:` fields link each definition back to the code that renders it.

## Maintain: keep it aligned, capture what only the running app knows

As the app evolves:

- **Re-iterate the affected pages.** Newly-orphaned nodes surface in coverage; existing entries (`memory`, descriptions, selector choices) are preserved.
- **Check the corpus against itself.** `sightmap validate` (schema, structure) and `sightmap lint` (advisory quality) — run in CI. This validates `.sightmap/` against itself; there is no static source-vs-YAML drift check, by design (the corpus is curated, not generated).
- **Capture runtime-only knowledge.** A quirk found during a session, a clarifying description, a newly-observed endpoint — these land as `memory` and new entries. Where a quirk can be *fixed* in the app rather than memorized, prefer that.

## The loop in one sentence

**The live page shows what's real; the agent names it and reconciles the YAML against it; `validate`/`lint` keep the corpus honest.**

None of the tools are required — `.sightmap/` is plain YAML and hand-authoring is fine — but together they keep curation cost close to zero as the app grows. See [Curator vs. consumer](/concepts/curator-vs-consumer) for which side of the format each tool sits on.
