`sightmap device` drives a native iOS app in the local iOS Simulator, or an Android app on an emulator or device ([Android](#android)), the way [`sightmap browser`](/cli/browser) drives Chrome. It reads the app's accessibility tree, applies your `.sightmap/` corpus with the same matcher as `sightmap snapshot`, and acts on elements by accessibility identifier or [component query](/cli/interaction#component-queries). Nothing leaves the machine except the app's own traffic.

<Note>
On iOS, `sightmap device` needs an Apple Silicon Mac, macOS 15 or later, and Xcode 26 or later selected with `xcode-select` (the Command Line Tools alone are not enough). On Android it needs `adb` from the Android SDK platform-tools. Run [`device doctor`](#device-doctor) first.
</Note>

## Conventions

- Every command takes `--json` (machine-readable output) and `--sightmap-dir` (default `.sightmap`). There is no upward search for the corpus, so run commands from the project root.
- `device start` records the session in `.sightmap/.device-session` and writes one run log per run to `.sightmap/.device-runs/<run>.jsonl`. Add both to `.sightmap/.gitignore`.
- Errors print one line, then a `Next:` line with the step to take.
- Coordinates are screen **points**, not pixels: a 390×844 pt screen is 1170×2532 px in a screenshot.

### Targets

`click`, `fill`, `scroll --in`, and `scroll --until` take one target:

| Target | Example | Resolves to |
|--------|---------|-------------|
| Snapshot id | `12` | Element 12 of the latest snapshot |
| Identifier | `login-submit`, `product.12` | The one element whose accessibility identifier is exactly this. A dotted identifier works bare, also in `scroll --until` before it is on screen |
| Component query | `ProductRow[title^="Product 15"]` | A component filtered on extracted properties; `LoginForm SignInButton` and `ProductRow#2` work as in the browser |
| Selector | `button[identifier="login-submit"]`, `[text="Not Now"]#0` | A CSS selector over the normalized tree, for elements no component names |

A target that matches several elements is an error that lists the candidates; add a predicate or append `#N`.

### Views without routes

The spec requires a `route` on every view, and native screens have no URL, so native corpora use short placeholder routes such as `/login`. `sightmap device` ignores routes: a snapshot uses the view whose own components match the most elements, marked `(inferred)`, unless you pass `--view`. SEP-0024 proposes a route-less `screen:` selector for this case; it is not part of the spec yet.

### Selectors on iOS

Each element exposes a role from its accessibility type (`button`, `text`, `textfield`, `securetextfield`, `switch`, `tab`, `cell`, `image`, `other`, and so on) and the attributes `identifier` (the `accessibilityIdentifier`, with `testid` as an alias), `text` (the label), and `value`.

Only accessible elements reach the iOS tree. An identifier on a plain wrapper view (a React Native `testID` on a non-accessible `View`, for example) never appears there, so `[testid="login-form"] [testid="login-submit"]` matches nothing. Write leaf selectors such as `[identifier="login-submit"]`.

The identifier is also the element's id, so `#login-submit` selects it. Identifiers often contain dots, which `#` reads as a class: escape them and single-quote the selector so YAML keeps the backslashes, as in `'#product\.1'`. Unescaped, `#checkout.submit` means id `checkout` with class `submit` and matches nothing, since native elements have no classes. A leading digit takes a hex escape, its code point followed by a space: `1.circle` is `'#\31 \.circle'`. `[identifier="1.circle"]` selects the same element and reads more easily.

```yaml .sightmap/views/login.yaml
version: 1
views:
  - name: Login
    route: /login            # placeholder; sightmap device ignores it
    components:
      - name: EmailField
        selector: '[identifier="login-email"]'
      - name: SignInButton
        selector: 'button[identifier="login-submit"]'
```

#### Splitting a combined label

A tappable container such as a SwiftUI `NavigationLink` row is one element whose label is its texts joined with `", "`, so `dom.text` reads `Trail Runner, Acme, $89.99`, not three values. A `pattern` splits it:

```yaml .sightmap/views/products.yaml
version: 1
views:
  - name: Products
    route: /products
    components:
      - name: ProductRow
        selector: '[identifier^="product."]'
        properties:
          - name: title
            extract: { from: dom.text, pattern: '^(.+?)(?:, [^,]+)?, \$[\d,]+(?:\.\d+)?$' }
          - name: brand
            extract: { from: dom.text, pattern: '^.+, ([^,]+), \$[\d,]+(?:\.\d+)?$' }
          - name: price
            extract: { from: dom.text, pattern: ', \$([\d,]+(?:\.\d+)?)$' }
```

The brand is optional, so `Trail Runner, $89.99` gives `title` and `price` and no `brand`, and a comma inside a title with a brand stays in `title`. The label carries no field boundaries, though, so no pattern can tell apart two cases that read the same: a title containing a comma with no brand (`Lamp, Large, $9.99` gives `title="Lamp"`, `brand="Large"`), and a brand containing `", "`. For an exact split, read each text from inside the app rather than from the combined label, or give each child its own identifier; treat a split label as a convenience for reading, not a value to assert on.

### `device start`

Boots the simulator, enables app accessibility, installs and launches the app, starts the session daemon, and begins a run log. The first time a simulator gets app accessibility, `start` reboots it once. Without `--detach`, `start` holds the shell as a foreground daemon; agents and scripts should pass `--detach`.

On a running session, `start` reinstalls (with `--app`) and relaunches the same app; after a reinstall the network sources are chosen again for the new build. It refuses a different app or device; run `device stop` first.

| Flag | Default | Description |
|------|---------|-------------|
| `--app` | none | The `.app` bundle built for the simulator, to install |
| `--bundle-id` | none | An installed app's bundle id (instead of `--app`) |
| `--device` | a booted simulator, else the newest iPhone | Simulator name or UDID |
| `--label` | none | Label for the run log |
| `--console-limit` | `5000` | How many console entries the session keeps |
| `--network` | `auto` | Network source: `auto`, `har`, `rn-cdp`, `summary` or `off` (see [`device network`](#device-network)) |
| `--network-limit` | `1000` | How many network entries the session keeps |
| `--metro-port` | the app's `RCT_jsLocation`, else `8081` | Where the `rn-cdp` source looks for Metro |
| `--detach` | off | Run the daemon in the background and return once it is ready |

```bash
sightmap device start --app build/SimSample.app --device "iPhone 17 Pro" --detach
```

```text
✓ simulator session started in 9.4 s
  device:  iPhone 17 Pro, iOS 26.0 (5D3E1A2B-7C8F-4E9A-B0C1-D2E3F4A5B6C7)
  app:     installed /Users/you/app/build/SimSample.app and launched org.sightmap.SimSample
  daemon:  pid 48213; session file .sightmap/.device-session; log /Users/you/Library/Caches/sightmap/device/sessions/5D3E1A2B-7C8F-4E9A-B0C1-D2E3F4A5B6C7/daemon.log
  run:     20261029T171502Z-3fa1 (`sightmap device run tail --follow` to follow)
  next:    sightmap device snapshot
```

Apps must be built by Xcode (`xcodebuild` or the Xcode app) so they carry the simulated entitlements a simulator app needs.

### `device snapshot`

Prints the annotated accessibility tree in the shape of [`sightmap snapshot`](/cli/capture): the view, a guide of matched components, the tree with per-snapshot ids, conflicts, and visible-only coverage. Matched elements show `[Component prop="value"]`; unmatched ones show `role[identifier="…"] "label"`.

| Flag | Default | Description |
|------|---------|-------------|
| `--view` | inferred | Apply this view's components instead of inferring the view |
| `--include-offscreen` | off | List off-screen elements too |
| `--out` | none | Also write the snapshot to this file, plus a `.tree.json` companion that `sightmap explain --snap` and `sightmap coverage` read |
| `--tree-out` | none | Write the tree JSON here |

```bash
sightmap device snapshot
```

```text
[View: Login] (inferred)

[Guide]
EmailField     1
PasswordField  1
SignInButton   1

--- component tree ---

1 application "Sightmap Sim Sample"
  2 text[identifier="login-title"] "Sightmap Sim Sample"
  3 [EmailField]
  4 [PasswordField]
  5 [SignInButton "Sign In"]

[Coverage] (visible only)
3 interactive · 3 direct T1 (100%) · 0 scoped T2 (0%) · 0 orphaned T3 ✓
```

Extra sections appear when they apply:

| Section | Meaning |
|---------|---------|
| `[Overlay]` | A system sheet from another process, such as iOS's "Save Password?", is in front of the app, and the tree is that sheet. Dismiss it with one of its buttons: `click '[text="Not Now"]'`. |
| `[Mostly empty]` | The app exposes no interactive elements, or only a small floating element, with the likely causes in order. |
| `[LogBox]` | A React Native LogBox toast covers the bottom of the screen; the section gives the `tap-xy` that hits its ✕. |
| `[Memory]` | `memory:` entries for the view and its matched components. |
| `[Conflicts]` | Elements matched by more than one component. |
| `[Off-screen]` | How many off-screen nodes were left out. Targets still resolve them. |

The corpus reloads whenever a YAML file under `--sightmap-dir` changes, so the next snapshot reflects your edits.

### `device click`

Resolves the target in a fresh read of the screen, checks that its center is on screen, not under the status bar or a navigation bar or outside the visible part of its list, not under a tab bar, toolbar, navigation bar, keyboard, LogBox toast, any control drawn over it (such as a custom tab bar of plain buttons over a list), or a floating dev-menu button, and that it is enabled, then taps its center. A switch is pressed for 0.15 s instead, at the trailing end of its row when it spans one (a SwiftUI `Toggle` in a `Form`): its label ignores taps, and an iOS 26 switch ignores most instant taps. While the target is missing or the screen is still moving, it re-reads for up to 3 s first. It taps only once two reads in a row agree on where the target and the screen are, and the screen has held still for 0.75 s. Two reads alone are not enough: the accessibility tree reports where an animation ends rather than where it is drawn, so a screen presented a moment ago reads the same throughout its slide, and iOS drops touches until a presentation finishes. A tap on a screen that was already still costs no extra wait. A screen still moving, or changed too recently, when the wait runs out is refused with an `unstable` error instead of being tapped mid-transition.

| Flag | Default | Description |
|------|---------|-------------|
| `--settle` | `3s` | How long to wait for a missing target or a moving screen, e.g. `5s` for a Debug React Native build that redraws slowly after a navigation |

```bash
sightmap device click SignInButton
```

```text
✓ clicked 6 [SignInButton "Sign In"] at (196, 412)
```

A refused click names the reason and the fix:

```text
error: 42 [ProductRow title="Product 40"] is off-screen (center 196,1210 on a 402x874 screen); refusing to tap
Next: run `sightmap device scroll down --until "ProductRow[title=\"Product 40\"]"`, then retry
```

### `device fill`

Taps the target, types the text, and errors if the field does not show it. Text is appended unless you pass `--clear`. `fill TARGET "" --clear` empties a field; a field that then shows only its placeholder reports an empty value.

| Flag | Default | Description |
|------|---------|-------------|
| `--clear` | off | Empty the field first |
| `--settle` | `3s` | As for `click` |

```bash
sightmap device fill login-email "a@example.com" --clear
```

```text
✓ filled 4 [EmailField "Email"] → value "a@example.com"
```

### `device scroll`

Scrolls one page in a direction (`up`, `down`, `left`, `right`), or until a target is tappable. Like `click`, it first waits for a screen that just changed to hold still for 0.75 s, so the swipe is not dropped mid-transition. Long SwiftUI and UIKit lists only expose rows near the screen, so a row further down is not found until you scroll to it. `--until` scrolls slowly enough not to fling past the target and refreshes the snapshot ids when it stops. A target that matches several elements stops the scroll at the first one that can be tapped, and the result says how many matched. `[text="…"]` matches a whole label; use `[text*="…"]` for part of one.

| Flag | Default | Description |
|------|---------|-------------|
| `--in` | the screen | Scroll inside this element |
| `--until` | none | Scroll until this target is tappable |
| `--max` | `20` | Give up after this many swipes |

```bash
sightmap device scroll down --until 'ProductRow[title="Product 40"]'
```

```text
✓ 42 [ProductRow title="Product 40"] is on screen after 5 scroll(s) down; snapshot ids refreshed, act on it by id 42 or by the same target
```

### `device console`

`console list` reads the app's own `os_log`/`Logger` output and its stdout and stderr, captured by the session daemon. `console get N` prints one entry in full.

| Flag | Default | Description |
|------|---------|-------------|
| `--limit` | `50` | The most recent N entries (`0`: all) |
| `--grep` | none | Case-insensitive substring of the message or subsystem |
| `--level` | all | Comma-separated levels: `debug`, `info`, `default`, `error`, `fault`, `stdout`, `stderr` |
| `--all` | off | Include Apple framework entries, hidden by default as noise |
| `--since` | none | Only entries after this index, oldest first; `--limit` then takes the first N, and the result's `last` is the index to page on from |
| `--follow` | off | Keep printing new entries until interrupted (with `--json`, one entry per line) |

The session keeps the latest 5,000 entries (`start --console-limit` changes that). When a list would have reached further back, it says so: `(N earlier entries dropped; …)`, or `dropped` in `--json`.

```bash
sightmap device console list --grep "signed in"
```

```text
#12 info    dev.sightmap.SimSample:app  signed in as agent@example.com
#13 stdout   signed in as agent@example.com
```

React Native `console.log` output arrives as `info` entries from the `com.facebook.react.log` subsystem.

### `device network`

`network list` lists the requests the app made, oldest first, each led by the [`requests:`](/spec/requests) definitions in your corpus that match it, as [`browser network list`](/cli/devtools) does, and trailed by the properties those definitions extract. `network get N` prints one entry with its headers and bodies.

```bash
sightmap device network list
```

```text
#0 [CreateOrder]          POST http://127.0.0.1:18765/anything/sightmap/order-1 → 201 (56 ms, har) {order=1, echoed=1}
#1 [--]                   GET https://api.example.com/v1/me → 200 (88 ms, har)
```

| Flag | Default | Description |
|------|---------|-------------|
| `--limit` | `50` | The most recent N entries (`0`: all) |
| `--grep` | none | Case-insensitive substring of the method, URL, status, source or matched request name |
| `--source` | all | Only entries from `har`, `rn-cdp` or `summary` |
| `--since` | none | Only entries after this index, oldest first, as in `console list` |
| `--follow` | off | Keep printing new entries until interrupted (with `--json`, one entry per line) |
| `--unredacted` | off | Show credentials (see *Redaction*) |
| `--request-file`, `--response-file` | none | `network get`: write the stored request or response body to a file, redacted unless `--unredacted` |

#### Sources

The session reads the app's traffic from the first of these sources that works; each entry's `source` says which one recorded it.

| Source | What it gives | Needs |
|---|---|---|
| `har` | Method, full URL with query, status, timing, request and response headers, and bodies up to 1 MiB, for everything that goes through `URLSession`/CFNetwork (including a React Native app's `fetch`) | The app's executable signed with the `get-task-allow` entitlement |
| `rn-cdp` | Method, full URL, the headers JavaScript set, request and response bodies, for a React Native Debug build's JS `fetch`/XHR only | Metro running, and a Debug build that reports to it |
| `summary` | Status, timing, byte counts and protocol, plus the method and host (`http://host`, no path). It never matches a `requests:` route | Nothing |

`--network auto` (the default) arms `har` before the app launches when the app has `get-task-allow`, and keeps `summary` as a backstop for requests HAR did not log. Without the entitlement it uses `summary` and looks for Metro every 2 s; once it attaches to the app's Metro page, `rn-cdp` replaces `summary` (which would list the same JS requests with less detail) until the connection drops, and it reattaches after a relaunch. `--network har`, `rn-cdp` or `summary` uses that source alone; `off` captures nothing. `device status` and `device doctor` report which source is active and why the others are not.

**`get-task-allow`.** CFNetwork logs HAR entries only for a process with this entitlement. A Debug build that Xcode signs for development carries it. A simulator build signed ad hoc (`CODE_SIGN_IDENTITY = "-"`) does not unless you add it: point `CODE_SIGN_ENTITLEMENTS` at a file containing

```xml
<key>get-task-allow</key><true/>
```

Release and App Store builds never have it, so they fall back to `summary`. `start` reads the entitlement from the executable and, when it is missing, `status` says so and why.

**How HAR capture works.** `har` switches on CFNetwork's own HAR logging inside the simulator, the mechanism Instruments' HTTP Traffic instrument uses, with private, undocumented CFNetwork preferences (`har-capture-global`, `har-body-size-limit`) and the `com.apple.CFNetwork` `HAR` log category; then it reads the simulator's unified log. Requests already under way when capture starts are missed. `stop` deletes the preferences and resets the log category. The capture is leased for 10 minutes at a time and renewed while the session runs, so a session that dies leaves it on for at most 10 minutes. A future iOS release may change these switches.

Only `URLSession`/CFNetwork traffic is visible to `har` and `summary`; raw sockets, SwiftNIO and other custom stacks are not. `rn-cdp` misses image loads and native modules' requests, and requests made before it attached.

#### Redaction

Output hides credentials by default: the values of the `Authorization`, `Cookie`, `Set-Cookie` and `Proxy-Authorization` headers, and of any header, query parameter, form field or JSON key whose name contains `token`, `password`, `secret` or `key` (case-insensitive) become `<redacted>`. Properties are extracted from the redacted entry, so a property that reads a credential shows `<redacted>` too. `--unredacted` shows everything.

The session keeps the latest 1,000 entries (`start --network-limit`) in memory, with each body capped at 256 KiB, and never writes them to disk: network entries and bodies stay out of the run log.

### `device run`

Every action appends one JSON line to `.sightmap/.device-runs/<run>.jsonl` with its timestamp, sequence number, arguments, target element, view, and outcome. Another agent or tool can follow a session with `run tail --follow`, or poll with `--since`, and line up its own data with the steps by timestamp. `launch` and `relaunch` are logged as such, so a restart is told apart from a first launch.

| Command | Description |
|---------|-------------|
| `device run new [--label L]` | Start a new run |
| `device run current` | Print the current run's id and path |
| `device run note TEXT [--kind K]` | Record an annotation in the run, e.g. `--kind session-start`, so a tool layered on top can mark its own events among the steps |
| `device run tail [--follow] [--since SEQ] [--run ID]` | Print run entries; `--follow` keeps printing new ones |

## How the simulator helper is distributed

The simulator is driven by a small Swift helper built on Meta's FBSimulatorControl, using the prebuilt xcframeworks from the idb v1.7.7 release (arm64 only). It reads the accessibility tree and sends touch, key, and button input.

The helper's sources are embedded in the `sightmap` binary. On first use (`device doctor` or `device start`), `sightmap` builds them with your local Xcode toolchain; Swift Package Manager downloads idb's frameworks (about 10 MB) during that build. Nothing else needs installing: no Homebrew, no `idb` or `idb_companion`. The build takes a minute or two and is cached under `~/Library/Caches/sightmap/device` (set `SIGHTMAP_DEVICE_CACHE` to move it). It rebuilds only when the embedded sources change. To use a helper you built yourself, set `SIGHTMAP_DEVICE_HELPER` to its path.

Sightmap builds the helper locally instead of shipping a prebuilt, signed binary for two reasons:

- The helper links Apple's private CoreSimulator and accessibility frameworks through FBSimulatorControl. Those frameworks track the installed Xcode, so a helper built against your Xcode matches it, while a prebuilt binary could break on the next Xcode release.
- `go install`, the npm package, and the release binaries stay identical, with no per-platform codesigning or notarization pipeline for a separate helper.

A new Xcode release can still need a sightmap update; `device doctor` says so when the helper fails to build.

## Android

`sightmap device` also drives an Android emulator or a connected device through `adb`, with the same commands, targets, run log, and corpus matching. It works on macOS, Linux, and Windows and needs only the Android SDK platform-tools: nothing is installed on the device besides your app.

```bash
sightmap device doctor --platform android
sightmap device start --app app/build/outputs/apk/debug/app-debug.apk --detach   # an .apk implies --platform android
sightmap device start --package com.example.app --device Pixel_8_API_35 --detach  # installed app; boots the AVD if it isn't running
```

- **Platform.** `--platform android` is implied by an `.apk` or `--package`, and is the default off macOS.
- **Device.** `--device` takes a serial from `adb devices`, a model, or an AVD name. An AVD that is not running is booted (one AVD and no device connected boots it without `--device`); if the emulator exits during boot, the error quotes its log, written to `$TMPDIR/sightmap-emulator-<AVD>.log`. On macOS a `QT_QPA_PLATFORM` other than `cocoa` is dropped from the emulator's environment, since it makes the emulator exit. `stop --shutdown` shuts down an emulator.
- **Tree.** Each snapshot is a `uiautomator dump` of the active window. uiautomator waits for a second without accessibility events before it dumps, so a read takes a second or more but is already settled: `click` and `scroll` act on one read, with neither the two reads that must agree nor the 0.75 s hold-still wait of iOS. The app needs no instrumentation and no setting turned on.
- **Points are dp.** Frames, `tap-xy`, and `swipe` use density-independent pixels: divide screenshot pixels by dpi/160 (2.625 on a 420 dpi device).
- **Identifiers.** `identifier` (and `testid`) is the view's resource-id without its package (`com.example:id/login_submit` becomes `login_submit`). Ids from AppCompat and Material Components layouts (a dialog's `parentPanel`, a bottom navigation item's `navigation_bar_item_icon_view`) are left out. Jetpack Compose `Modifier.testTag` values appear only when the app sets `Modifier.semantics { testTagsAsResourceId = true }` on an ancestor. A dialog, bottom sheet, or popup is a window of its own and needs it again inside. A snapshot of Compose content with no identifiers at all says so under `[No identifiers]`.
- **Roles.** Widget classes map to the iOS roles: `Button` and `ImageButton` to `button`, `TextView` to `text`, `EditText` to `textfield` (`securetextfield` for passwords), `CheckBox`, `Switch`, `RadioButton`, `ImageView` to `image`, `RecyclerView`/`ListView` to `collection`, `ScrollView` or any scrollable view to `scrollview`, tabs to `tab` (see below), everything else to `other`. Compose reports a role on an empty node under the element; the element takes it, so a Compose `Button` is a `button`, a segmented button a `radio`, and a checkbox row a `checkbox`. A checkable element with no role (a Compose `Switch`, a `Modifier.toggleable` row) is a `switch`. Tabs are `tab` inside a `tabbar`, with `(selected)` on the current one. No tab class reaches the dump, so a row is tabs when a library marks it (Material `BottomNavigationView` and `NavigationRailView` items, a `TabWidget`'s children) or when it is laid out as a tab bar: labelled tappable items side by side, exactly one selected, along the top or bottom edge of the screen. That covers a Compose `NavigationBar` or `TabRow`, a `TabLayout`, and React Navigation's tabs; a segmented control in the middle of the screen is not a tab bar. As on iOS, the tab bar covers what scrolls under it, so a tap there is refused. A clickable `other` without text (a list row, a Compose `Modifier.clickable` row) is named by its children's text, and a single text is folded into it as on iOS; several texts stay as children, so child components can read each one. `checked` (on every checkable element, toggle-group segments included), `selected`, and `disabled` go into the state. Compose leaves the click action off the selected tab or segment; it still counts as interactive.
- **Fields.** A field's label is its hint or content description (or a Compose text field's label text) and its value is its text. An empty Material `TextInputLayout` field reports its hint as its text, so it reads as filled with it.
- **Overlays.** A window from another package (a runtime permission dialog, an autofill prompt) appears as `[Overlay]`, named by its package.
- **Status bar.** Taps are kept off the status bar as on iOS, using its height from `dumpsys window StatusBar` (24 dp if that can't be read), so a toolbar button just below it stays tappable.
- **Keyboard.** The keyboard is read from `dumpsys window InputMethod` and covers what is under it, as on iOS. On recent Android the input method window spans the whole screen and is transparent above the keys, so the keyboard is taken from its touchable region (or its content insets), not its frame. Gboard on an emulator with a hardware keyboard shows a small floating toolbar instead of a keyboard; it appears as its own `keyboard` node. `device button back` hides it.
- **Input.** A switch gets the same 0.15 s press at the trailing end of its row (`input swipe` with one point), which Android takes as a tap anywhere on the row. `type` and `fill` go through `adb shell input text`, which types ASCII only. `key` takes the same names as on iOS; `button` takes `home`, `back`, `menu`, `app_switch`, `lock`, `volume_up`, `volume_down`.
- **Network.** `network list` / `get` and `--network` are iOS-only for now; on Android they fail with `unsupported`.
- **Console.** `console` reads logcat lines from the app's process: the tag is the subsystem, levels are `debug`, `info`, `warning`, `error`, `fault`, and `System.out` / `System.err` read as `stdout` / `stderr`.

### Setting up from nothing

On a Mac with nothing installed, this sets up an emulator without Android Studio:

```bash
brew install openjdk@17 && brew install --cask android-commandlinetools
export JAVA_HOME=/opt/homebrew/opt/openjdk@17/libexec/openjdk.jdk/Contents/Home
export ANDROID_HOME=$HOME/Library/Android/sdk
SDKM=/opt/homebrew/share/android-commandlinetools/cmdline-tools/latest/bin/sdkmanager
yes | $SDKM --sdk_root=$ANDROID_HOME --licenses
$SDKM --sdk_root=$ANDROID_HOME --install "cmdline-tools;latest" platform-tools emulator \
  "platforms;android-35" "build-tools;35.0.0" "system-images;android-35;google_apis;arm64-v8a"
export PATH="$ANDROID_HOME/platform-tools:$ANDROID_HOME/emulator:$ANDROID_HOME/cmdline-tools/latest/bin:$ANDROID_HOME/build-tools/35.0.0:$PATH"
avdmanager create avd -n Pixel_8_API_35 -k "system-images;android-35;google_apis;arm64-v8a" -d pixel_8
sightmap device doctor --platform android
```

`build-tools` on `PATH` provides `aapt2`, which `start --app` uses to read an APK's package name. A cold boot of the AVD takes about 80 s; later boots from its snapshot take under 20 s. If an app never reaches its first screen, `adb logcat -d -b crash` has the reason.

If a snapshot fails with "could not get idle state", the screen never stopped animating; turn off animations with `adb shell settings put global animator_duration_scale 0` (and `transition_animation_scale`, `window_animation_scale`). uiautomator can't run alongside another UI automation client such as an Appium UiAutomator2 server.

## Limits

- On iOS, simulator only, on Apple Silicon. Physical iOS devices are not supported.
- No hover or file upload. For another screen size, start on a different `--device`.
- `click` confirms the tap was delivered, not that the app handled it. On iOS 26, a screen with a hidden search field and search scopes can have an invisible strip up to ~35 pt below the navigation bar that swallows touches (a real finger's too), with nothing in the accessibility tree to show it. Check the result with `snapshot` and, if nothing changed, use `tap-xy` lower in the target.
- Network capture covers `URLSession`/CFNetwork traffic (and, for React Native Debug builds, JS traffic through Metro); full detail needs the `get-task-allow` entitlement.

The `sightmap-device` agent skill covers the full agent workflow, including React Native specifics. Install it with [`sightmap skills install`](/cli/integrate#sightmap-skills-install).
