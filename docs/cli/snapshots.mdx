A page can render different components across loads because of lazy content, personalization, rotating promotions, or user interaction. Sightmap stores multiple captures as a view set. This page covers the on-disk layout, the novelty gate, and the commands that compare, prune, and migrate captures.

<Note>
`snapshot` and `iterate` create captures; see [Capture commands](/cli/capture). `coverage`, `multi-coverage`, and `report` read saved view sets; see [Coverage commands](/cli/coverage).
</Note>

## The capture layout

New view-set captures live at `.sightmap/snapshots/{view}/{stamp}.snap`. `{stamp}` is a UTC timestamp in `YYYYMMDDTHHMMSSZ` form, so lexical and chronological order match:

```text .sightmap/snapshots/
.sightmap/
└── snapshots/
    ├── home/
    │   ├── 20260607T193000Z.snap
    │   ├── 20260607T193000Z.snap.tree.json
    │   ├── 20260608T001500Z.snap
    │   └── 20260608T001500Z.snap.tree.json
    └── plp/
        ├── 20260722T141230Z.snap
        └── 20260722T141230Z.snap.tree.json
```

Two files per capture:

- **`{stamp}.snap`** contains the human-readable annotated tree.
- **`{stamp}.snap.tree.json`** contains the raw component tree used by `coverage`, `multi-coverage`, `sel-check`, and `snapshot-novelty`.

Captures do not have curated state names. To cover an open drawer, a selected tab, or another page state, capture the view in that state. The novelty gate adds it to the set only if it contributes new structure.

## A view is a set

`snapshot` appends to the view's set instead of overwriting an existing capture. Each reader handles the set differently:

- `coverage` reports tiers for each capture and flags a component dead only when it matches none of the captures.
- `report` rolls each set up to one row, with T1/T2 as weighted averages and T3 as the maximum across captures.
- `multi-coverage` folds each set into one matrix column whose cells are per-component maximums.

A component can therefore be absent from one capture without being reported as dead for the view.

## The novelty gate

The novelty gate keeps a capture only when it adds structure to the view's existing set:

- A component type that no existing capture matches.
- An orphan slot that no existing capture contains. A slot is identified by the node's role and nearest `data-testid` or `data-component` ancestor.

Changes to products, prices, or copy within the same structure do not count. The first capture always writes, `--force` bypasses the gate, and `--out FILE` writes outside the set without applying the gate.

Novelty depends on the current corpus. The command re-matches saved captures whenever it compares them. A capture kept for unique orphans can become redundant after new component definitions cover those nodes.

---

### `snapshot-novelty`

Reports whether a saved capture adds a component type or orphan slot that does not appear elsewhere in its view's set.

**Flags:**

| Flag | Default | Description |
|------|---------|-------------|
| `--sightmap-dir` | `.sightmap` | Path to the `.sightmap/` dir. |

```bash
sightmap snapshot-novelty .sightmap/snapshots/plp/20260722T141230Z.snap
```

```text
plp · candidate 20260722T141230Z.snap vs 3 existing capture(s)

Novel components (matched here, in no existing capture):
  QuickViewModal

Novel orphan slots (uncovered interactive nodes, new vs the set):
  2× button @ div[data-testid="quick-view"]

→ NOVEL: adds 1 component, 1 orphan slot — keep.
```

A redundant capture reports the opposite verdict:

```text
plp · candidate 20260722T141230Z.snap vs 3 existing capture(s)

nothing new vs 3 capture(s) — redundant.
```

---

### `snapshot-prune`

Re-matches every capture in a view against the current corpus and removes captures whose component types and orphan slots all appear in the remaining set. Pruning runs iteratively, never removes the last capture, and reduces identical captures to one. Pass a view name, or use `--all` for every view with captures.

**Flags:**

| Flag | Default | Description |
|------|---------|-------------|
| `--all` | `false` | Prune every view with captures. |
| `--dry-run` | `false` | Report what would be pruned without deleting. |
| `--sightmap-dir` | `.sightmap` | Path to the `.sightmap/` dir. |

```bash
sightmap snapshot-prune --dry-run plp
```

```text
plp: 5 capture(s) → keep 3, would prune 2
  would prune 2026-06-07 19:30Z
  would prune 2026-06-08 00:15Z

(dry run — nothing deleted; re-run without --dry-run to prune)
```

Re-run without `--dry-run` to delete the listed captures along with their `.snap.tree.json` siblings.

<Tip>
Run `snapshot-prune --dry-run --all` after adding component definitions. Review the proposed removals before running it again without `--dry-run`.
</Tip>

---

### `migrate-snapshots`

Moves legacy flat `.snap` files and their `.snap.tree.json` siblings from the current directory to `.sightmap/snapshots/{view}/base.snap`. The command derives the view directory from the filename. Run with `--dry-run` first to print each planned move as an `old → new` line.

Coverage and view-set commands continue to read legacy flat captures during migration.

**Flags:**

| Flag | Default | Description |
|------|---------|-------------|
| `--dry-run` | `false` | Show what would be moved without actually moving files. |
| `--sightmap-dir` | `.sightmap` | Path to the `.sightmap/` dir. |

```bash
sightmap migrate-snapshots --dry-run
```

```text
home.snap → .sightmap/snapshots/home/base.snap
home.snap.tree.json → .sightmap/snapshots/home/base.snap.tree.json
plp.snap → .sightmap/snapshots/plp/base.snap
plp.snap.tree.json → .sightmap/snapshots/plp/base.snap.tree.json

migrate-snapshots: dry run complete, 2 files would be moved
```

## Typical flow

<Steps>
  <Step title="Build the set">
    Capture each relevant page state, such as a fresh load, an open drawer, or a selected tab. The novelty gate keeps captures that add a component type or orphan slot.
  </Step>
  <Step title="Check a candidate when in doubt">
    Run `sightmap snapshot-novelty FILE.snap` to see what a capture adds relative to the rest of its set.
  </Step>
  <Step title="Author against the union">
    Follow the [coverage loop](/cli/coverage) until every capture has zero T3 orphans. New component definitions may make older captures redundant.
  </Step>
  <Step title="Prune the redundant captures">
    Run `sightmap snapshot-prune --dry-run --all`, review the plan, then run it again without `--dry-run`. The remaining captures preserve the same component types and orphan slots.
  </Step>
</Steps>
