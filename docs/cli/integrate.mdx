`sightmap add` installs a published corpus from the community atlas. `sightmap serve-sightmap` serves the compiled corpus as JSON and recompiles it when YAML changes. `sightmap skills install` extracts the bundled agent skills. `sightmap version` prints the binary version.

<Note>
`sightmap browser start` runs the same HTTP server alongside Chrome. Use `serve-sightmap` when you need the corpus endpoint without a managed browser session. See [Browser](/cli/browser) for session management.
</Note>

---

### `sightmap add`

Installs a corpus published in the community atlas ([github.com/sightmap/atlas](https://github.com/sightmap/atlas)) into `--target` (default `.sightmap`), so you can start from someone else's map of a site instead of authoring one from scratch. `SLUG` is the entry's identifier on its gallery page.

The command reads the atlas index, resolves `SLUG` to an entry, fetches that entry's files, and writes them under the target with the leading `.sightmap/` stripped — so `--target` may be named anything. Flags work before or after `SLUG`.

**Flags:**

| Flag | Default | Description |
| --- | --- | --- |
| `--force` | off | Install into a non-empty target directory, replacing its contents |
| `--index` | `https://raw.githubusercontent.com/sightmap/atlas/main/index.json` | Atlas `index.json` URL (for mirrors and tests) |
| `--target` | `.sightmap` | Directory to install the corpus into |

```bash
sightmap add acme-shop
```

```text
  wrote  .sightmap/config.yaml
  wrote  .sightmap/components.yaml
  wrote  .sightmap/views/plp.yaml

Installed acme-shop (Acme Shop): 3 files → .sightmap. Next:
  sightmap validate
```

An unknown slug lists the closest published slugs and exits 1:

```text
sightmap add: no atlas entry with slug "acme" — closest matches:
  acme-admin
  acme-shop
```

`add` never merges into an existing corpus. If the target has contents, it stops without fetching anything:

```text
sightmap add: install target already exists and is not empty: .sightmap — pass --force to replace it
```

`--force` replaces the target wholesale rather than merging, so files the entry no longer publishes do not survive:

```text
  wrote  .sightmap/config.yaml
  wrote  .sightmap/components.yaml
  wrote  .sightmap/views/plp.yaml
  replaced the previous contents of .sightmap

Installed acme-shop (Acme Shop): 3 files → .sightmap. Next:
  sightmap validate
```

**What `add` guarantees.** A `--index` URL you were handed by a stranger is untrusted input, and so is every string inside the index it points at. The command enforces the following, whatever the index says:

| Guarantee | What it covers |
| --- | --- |
| HTTPS only | Both the index and every file are fetched over `https://`. Plain `http://` is refused except for loopback hosts (`localhost`, `127.0.0.1`, `::1`), so local mirrors and tests still work. The check is re-applied to every redirect hop, so a `302` cannot downgrade a fetch to plaintext after the fact. Chains stop after 5 redirects. |
| Fail-closed paths | An entry's slug, commit, and file paths are validated before they reach a URL or the filesystem. A slug with a path separator or `..`, a file path outside `.sightmap/`, a backslash, a relative segment, or any control character (including `ESC`, the terminal-escape injection vector) refuses the whole install. Atlas-supplied text is escaped before it is printed. |
| Commit pinning | When an entry publishes a 40-character commit, its files are fetched at that commit, so the index and the content cannot straddle an atlas push. An unpinned entry is fetched at the index's own ref and says so on stderr. |
| Atomic install | Every file is fetched before any is written, the result is staged in a temporary directory, and the staged corpus is loaded to prove it works before a rename swaps it into place. A failed install — a 404, a broken entry, a full disk — leaves the target exactly as it was. |
| Size caps | 8 MiB for the index, 4 MiB per file, and 32 MiB and 256 files per entry — the file limit is checked before the first file is requested. Each fetch also has a 30-second timeout, but a timeout bounds how long a response takes, not how large it is; the byte caps are what stop a hostile mirror. |

An entry with no published commit warns, because the guarantee above is the one it cannot offer:

```text
warning: atlas entry "acme-admin" publishes no commit, so its files were fetched from the floating ref "main" — the index and the files can straddle an atlas push
```

<Warning>
What `add` does **not** do is vet the corpus's content. It proves the YAML loads and refuses paths that would escape the target; it does not check that the selectors are right, that the entry belongs to whoever the name suggests, or that anyone reviewed it. A corpus is data, not code sightmap executes — but its `description:` and `memory:` text is read by your agent, so treat an unfamiliar atlas or `--index` host the way you would treat any other package source. Run `sightmap validate` and read the YAML before you trust it.
</Warning>

### `sightmap serve-sightmap`

Compiles the `.sightmap/` corpus and serves it over HTTP on port 7891 by default. Two endpoints:

| Endpoint | Returns |
| --- | --- |
| `GET /sightmap` | The compiled corpus JSON: `site`, `version`, `views` (name and route), `globals`, and `viewComponents` keyed by route |
| `GET /sightmap/version` | A version-only response for polling clients: `{"version":"..."}` |

The `version` value is a Unix-millisecond timestamp created with each compile. Both endpoints set `Access-Control-Allow-Origin: *`.

The server watches `.yaml` and `.yml` files under `.sightmap/` and recompiles 200 ms after the last filesystem event. It excludes the `snapshots/` and `review/` directories, so writing captures does not change the corpus version.

The bundled browser extension fetches the corpus for its side panel and DevTools integration. `browser start` extracts the extension to `~/.sightmap/extension/` when it is missing or its bundled version has changed.

**Flags:**

| Flag | Default | Description |
| --- | --- | --- |
| `--port` | `7891` | HTTP port to listen on |
| `--sightmap-dir` | `.sightmap` | Path to the `.sightmap/` directory |

```bash
sightmap serve-sightmap
```

```text
[serve-sightmap] listening on http://:7891
```

After a YAML change, the server logs `[serve-sightmap] recompiled (v1753208412345)` with the new version value.

Fetch the compiled corpus:

```bash
curl -s localhost:7891/sightmap
```

```json
{
  "site": "example-shop",
  "version": "1753208412345",
  "views": [
    { "name": "plp", "route": "/b/**" },
    { "name": "pdp", "route": "/p/**" }
  ],
  "globals": [
    {
      "name": "SiteHeader",
      "selector": "header[data-testid=\"site-header\"]",
      "parentChain": [],
      "properties": []
    }
  ],
  "viewComponents": {
    "/b/**": [
      {
        "name": "ProductPod",
        "selector": "[data-testid=\"product-pod\"]",
        "parentChain": [],
        "properties": [
          { "name": "label", "extract": "h3" }
        ]
      }
    ],
    "/p/**": []
  }
}
```

`site` is the basename of the directory the server was started in. Each component carries its `name`, a comma-joined `selector` string, a `parentChain` (always an array, empty for top-level components), and its `properties`.

<Warning>
The `properties` entries reflect property extraction (`properties:` on components), which the CLI implements as a draft extension — it is not part of spec v1 and may change.
</Warning>

### `sightmap skills install`

Extracts the two agent skills embedded in the binary, each into its own subdirectory of the target directory:

- **`sightmap-authoring`**: the corpus authoring playbook, including the edit-verify loop, coverage tiers, selector rules, and quality checks.
- **`sightmap-browser`**: instructions for reading annotated snapshots and interacting with a live browser by component query.

The default target is `~/.agents/skills/`. The command removes any existing directory for each bundled skill before extracting the new copy.

**Flags:**

| Flag | Default | Description |
| --- | --- | --- |
| `--target` | `~/.agents/skills` | Directory to install skills into (each skill becomes a subdirectory) |

```bash
sightmap skills install
```

```text
installed 2 sightmap skill(s) → /Users/you/.agents/skills
  sightmap-authoring
  sightmap-browser
  version: 0.13.1
```

<Tip>
The skills are embedded in the binary. Run `sightmap skills install` again after upgrading the CLI.
</Tip>

### `sightmap version`

Prints the version and exits. No flags.

```bash
sightmap version
```

```text
sightmap version 0.13.1
```

Releases are published on [GitHub Releases](https://github.com/sightmap/sightmap/releases); see [Install](/start/install) for the npm and `go install` paths.

## Typical flow

<Steps>
  <Step title="Install the skills">
    Run `sightmap skills install` to extract `sightmap-authoring` and `sightmap-browser` under `~/.agents/skills/`.
  </Step>
  <Step title="Start from a published corpus, if there is one">
    Check the atlas for the site you are mapping. If an entry exists, `sightmap add SLUG` writes it into `.sightmap/`; run `sightmap validate` and read the YAML before building on it.
  </Step>
  <Step title="Serve the corpus">
    Start a full session with `sightmap browser start` (the server is included), or run `sightmap serve-sightmap` standalone when you only need the HTTP endpoint.
  </Step>
  <Step title="Consume the endpoints">
    Point your tooling at `GET /sightmap` for the compiled corpus and poll `GET /sightmap/version` to detect changes. The overlay extension does exactly this.
  </Step>
  <Step title="Edit YAML and let it reload">
    Save a `.yaml` or `.yml` file under a watched corpus directory. The server recompiles 200 ms after the last filesystem event and changes the version value. Polling clients can then fetch the new corpus.
  </Step>
</Steps>
